## scout-zero-candidates — Scout agent intermittently returns zero charity candidates, RuntimeError kills the whole run
- **Date:** 2026-07-17
- **Error patterns:** scout, RuntimeError, zero charity candidates, corrective retry, LLM returned zero, Tavily surfaced 15 results, empty candidates list, ScoutBatchOutput, status=failed, structured output, discover_candidates
- **Root cause:** `ScoutBatchOutput.candidates` has no `min_length`, so `{"candidates": []}` is fully schema-valid — `acomplete()`'s internal regenerate (fires only when `parsed is None`) never engages for an empty list. The sole defense was ONE Python-level retry in `discover_candidates()` that re-sent the same Tavily results with only "you must return 3+" appended, never addressing WHY the model rejected everything. Scout's system prompt (`prompts/scout.md`) tells the model to strongly reject anything "Charity Navigator already ranks prominently"; because `SCOUT_QUERIES` are generic rather than charity-name-targeted, they can surface a batch that is mostly well-known/listicle content, letting the model self-consistently reject all 15 results — a state a same-message retry cannot break out of. NOTE: this is LLM sampling behavior, so the "root cause" is a missing-resilience defect, not a single deterministic code bug.
- **Fix:** PROBABILISTIC MITIGATION, NOT A VERIFIED FIX. Widened the retry budget from 1 retry (2 LLM calls) to 2 retries (3 LLM calls) via a new `SCOUT_EMPTY_RETRY_MESSAGES` tuple + a bounded loop that breaks as soon as candidates are non-empty (happy path unchanged). Made retries escalate rather than repeat: retry #2 names the likely failure mode and authorizes relaxing the obscurity/prominence bar. Verified deterministically only at the mechanism level via mocked `acomplete`; real confirmation requires watching the Convex `runs` table for recurrence. Commit 9d3b29b.
- **Files changed:** packages/pipeline/src/eisenbalm_pipeline/agents/scout.py, packages/pipeline/tests/agents/test_scout.py
- **Eliminated (do not re-investigate):** `featured_keys` over-exclusion (live registry has only 1 featured row => 2 dedup keys; corrupted `timesFeatured: 33886` is never read by `listForDedup`); max_tokens truncation (12k budget vs 343 observed `tokens_out`); Tavily content not reaching the prompt (`_build_messages` interpolates real title/url/content); stub mode (`stubMode:false` in prod); `_extract_candidates` dropping a populated list.
- **Open follow-ups:** (1) log the actual Tavily titles/URLs/content on the zero-candidate path — nothing currently captures what the model saw, which is the evidence needed if this recurs; (2) revisit `SCOUT_QUERIES` (live registry contains candidate rows with `gofundme.com` / article-URL domains, i.e. Scout has been parsing listicles, not charity homepages); (3) PRE-EXISTING: `discover_candidates` overwrites `usage` on every retry, so retried attempts vanish from the per-run cost blob (`"scout": {..., "retries": 0}` is untrustworthy on a retry path) — accumulate instead of overwrite.

## scout-zero-candidates (recurrence) — retry-budget mitigation alone was insufficient; true root cause was query content, not model over-rejection
- **Date:** 2026-07-22
- **Error patterns:** scout, RuntimeError, zero charity candidates, corrective retry, LLM returned zero, Tavily surfaced 15 results, empty candidates list, ScoutBatchOutput, status=failed, structured output, discover_candidates, SCOUT_QUERIES, guidestar
- **Root cause:** The 07-17 fix (widened retry budget, escalating instructions) did NOT stop recurrence on 2026-07-20/07-21. Live reproduction (real Tavily + real OpenRouter Haiku, twice) proved the DOMINANT cause is not the model over-applying its "reject anything Charity Navigator-ranked" rule — it's that the 3 original `SCOUT_QUERIES` ("obscure charity small nonprofit overlooked impact", "underfunded charitable foundation lesser-known", "small charity unique mission narrow focus") reliably surface meta-commentary/analysis/how-to content ABOUT the nonprofit sector (blog posts, YouTube videos, donor-advice pages, "10 mission statement examples" listicles) that never names a SPECIFIC charity at all. The model's `{"candidates": []}` response (tokens_out=8) is genuinely correct given zero-extractable input — not a refusal, not truncation, not a parse bug. Because the retry loop re-sends the SAME stale Tavily results on every attempt (by design — "do not run new searches"), no retry wording can recover a genuinely orgless batch. A control test with synthetic-but-realistic charity content through the same real LLM call correctly extracted candidates, ruling out any broader prompt/parse/model defect.
- **Fix:** Extended `SCOUT_QUERIES` from 3 to 5, adding 2 live-validated `site:guidestar.org/profile`-targeted queries (empirically confirmed to reliably return individual charity profile pages with real names + mission text — e.g. "Foster Love", "No Baby Blisters", "Emerald Development and Economic Network"). Kept the original 3 for diversity; kept the 07-17 escalating-retry loop unchanged as defense-in-depth (no longer the primary defense). Added WARNING-level instrumentation logging the actual Tavily titles/URLs on the first empty attempt (closes the 07-17 session's follow-up #1 gap). Verified live: 2/2 consecutive real end-to-end `discover_candidates()` runs succeeded on the first LLM attempt post-fix (4 genuinely obscure charities each time, no retry needed). Full pipeline suite: 715 passed, 0 failures.
- **Files changed:** packages/pipeline/src/eisenbalm_pipeline/agents/scout.py, packages/pipeline/tests/agents/test_scout.py
- **Eliminated (do not re-investigate):** H1 post-filter dedup as the cause of THIS RuntimeError (the raise fires on raw LLM output before the dedup step is ever reached — dedup happens later and is architecturally unreachable when this error fires); H2 structured-output/acomplete() silently swallowing an error as empty (production logs show scout.py's own retry-loop warning, not acomplete's distinct "schema miss" warning — meaning `parsed` was a valid, non-None, genuinely-empty `ScoutBatchOutput` each time); max_tokens/model misconfiguration (scout uses haiku-4-5, temp 0.3, max_tokens=12_000 — not opus, not null; tokens_out=8 for the empty case is far under budget, not a truncation signature).
- **Open follow-ups:** (1) PRE-EXISTING, still not fixed (deliberately out of scope both sessions): `discover_candidates` overwrites `usage` on every retry rather than accumulating — cost blob undercounts retried attempts; (2) `prompts/scout.md` still contains a vestigial "Max tool calls: 8" / "emit as soon as you have enough information" instruction referring to agentic tool-calling behavior the LLM no longer performs (all searches happen in Python before a single non-tool-calling structured-output call) — harmless but worth cleaning up; (3) if this recurs a THIRD time despite both fixes, the new WARNING-level Tavily-titles log (added this session) should make instant diagnosis possible — check Railway logs for "LLM returned zero candidates on first attempt. Tavily batch (...) was: [...]" before re-investigating from scratch.
