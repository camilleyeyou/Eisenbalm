# Quick Task 260718-51o: Failed runs must not present a working-looking review surface Summary

**Failed pipeline runs are now a first-class terminal `IssueStatus`/`StageState`/task-list state across dispatch-control, and the Approval route renders an honest "this run failed" panel with a Run Monitor recovery link instead of mounting the sign-off DecisionRail that could only 409.**

## Performance

- **Duration:** ~25 min
- **Tasks:** 2
- **Files modified:** 6

## Accomplishments
- `deriveIssueStatus` returns `'failed'` (never `'needs-review'`) for a failed run, with published/held precedence preserved
- `deriveStageStates` returns all-`not-generated` for a failed non-published run — no stage shows `'needs-you'` — via a single guard at the top of the aggregator, not five separate edits
- `deriveTasks` returns `[]` for a failed run, so My Tasks and the header open-count no longer advertise sign-off actions that can only 409
- All three `Record<Exclude<IssueStatus,'unknown'>,...>` consumers (issue workspace layout, IssueCard, Masthead) render `'failed'` as a non-actionable "Run failed" label — type-checked by `pnpm build`, not just vitest
- The Approval route (`/issues/[n]/approval`) renders a terminal panel — heading, plain-language explanation, the run's `errorMessage` when present, and links to `/run-monitor/runs/{runId}` (recovery) and back to the issue — instead of mounting `ApprovalStage`/`DecisionRail`

## Decisions Made
- Extended the `IssueStatus` union with `'failed'` rather than adding a parallel boolean, so the compiler enforces coverage at all three `STATUS_META` sites (this was the deliberate design point of the plan — vitest alone cannot catch a missing record key, only `pnpm build` can)
- Single guard at the top of `deriveStageStates` rather than touching all five internal stage functions — smaller diff, same effect, and it stays robust to a (currently impossible) published+failed combination by checking `!i.issue?.published`
- The Approval route renders rather than redirects on a failed run, consistent with the codebase's "always explain, never silently bounce" convention already established by `RunDetail.tsx`'s `RecoveryRail`
