# Quick 260717-35u: Fix FastAPI error envelope unwrapping across dispatch-control clients Summary

Fixed 3 of 8 `apps/dispatch-control/lib/*Client.ts` files (4 call sites total) that read
`reason`/`message` directly off FastAPI's raw JSON body instead of unwrapping the
`HTTPException` envelope shape `{detail: {reason, message}}` — every 4xx from these
3 clients surfaced as `reason: 'unknown'` / `message: 'HTTP <status>'` regardless of
what the server actually said, silencing operator-facing remediation copy
(e.g. "Both sign-offs (Facts cleared + Sounds human) are required.").

## What Was Built

**Task 1 — RED regression test (`errorEnvelope.test.ts`)**
New test file driving the REAL un-mocked `_reviewFetch`/`_signOffFetch`/contentPatch
parse path via public exports (`publishIssue`, `recordSignOff`, `patchSection`), stubbing
`fetch` to return FastAPI's true wire shape — deliberately not constructing
`ReviewApiError`/`SignOffApiError`/`ContentPatchError` directly (that's the exact blind
spot in the pre-existing `DecisionRail.test.tsx` that let this bug ship). 7 tests: the
3 previously-broken sites (reviewClient 409, signOffClient 409, contentPatchClient
`fields` bug), plus 4 preserved-behavior locks (plain-string `detail`, 422 array
passthrough, non-JSON body → `res.text()` fallback, flat non-enveloped body).

Confirmed RED against the unfixed code: Tests 1–3 failed with the exact predicted wrong
values (`reason: 'unknown'`, `message: 'HTTP 409'`, `fields: undefined`) — proof the test
exercises the broken parse block, not a mocked error object. (One additional test,
"plain-string detail", also failed pre-fix against `reviewClient.ts`'s specific broken
code — a related pre-existing gap not explicitly called out in the plan's test-numbering,
but one the canonical idiom fixes as a side effect; not a scope change.)

**Task 2 — Unwrap the envelope at all 4 call sites**
Applied the established idiom verbatim from `lib/voicePassClient.ts` (already correct,
and already correct in `briefClient.ts`, `revisionClient.ts`, `factCheckClient.ts`,
`findingsClient.ts` — 5 of 8 total) to:
- `reviewClient.ts` `_reviewFetch` (~line 83)
- `signOffClient.ts` `_signOffFetch` (~line 77)
- `contentPatchClient.ts` `_contentFetch` site 1 (~line 198) — plus repointed the
  `if (Array.isArray(detail?.fields)) fields = detail.fields` line at the now-unwrapped
  `detail` (the line itself didn't need rewriting, only the unwrap above it)
- `contentPatchClient.ts` `uploadAsset` site 2 (~line 390)

No `XxxApiError` constructor signatures changed. No UI reason-branch vocabulary touched —
`claims_not_signed_off` in `ReviewDecisionPanel.tsx` is untouched (confirmed via `git diff`
against both commits: 0 hits), since that reason is still legitimately emitted by the
facts-cleared sign-off endpoint.

## Deviations from Plan

### Environment note (not a code change)

`pnpm --filter dispatch-control build` initially failed with "Could not find Convex client!"
during static-page prerendering (`/how-to-use` in this worktree; `/` when reproduced against
the pre-fix baseline via `git stash`). This worktree has no `.env.local` — only `.env.example`
— so `NEXT_PUBLIC_CONVEX_URL` was unset for the local build. Confirmed via `git stash` that
this failure reproduces identically on the pre-fix commit (fails on a different page, same
root cause), proving it is a pre-existing sandboxed-worktree environment gap, not something
introduced by this task's 4-site fix. Supplied `NEXT_PUBLIC_CONVEX_URL` (from `.env.example`,
the project's known dev deployment `modest-magpie-797`) as a build-time env var — not a code
or config file change — and the build then exited 0 cleanly with all 32 routes generated and
no type errors. No files were modified to work around this; it was purely a missing shell
env var for this build invocation.

### Diagnosis corrections (per plan's `<scope_correction>`, carried into this summary as requested)

- The incoming diagnosis claimed all 8 clients shared the identical broken block. Verified:
  **false** — only 3 of 8 were broken (`reviewClient.ts`, `signOffClient.ts`,
  `contentPatchClient.ts`); `briefClient.ts`, `revisionClient.ts`, `factCheckClient.ts`,
  `findingsClient.ts`, `voicePassClient.ts` were already correct.
- The diagnosis listed `contentPatchClient.ts` as a single broken site; it actually had
  **two** (`_contentFetch` and `uploadAsset`), plus a bonus bug the diagnosis missed: the
  `fields` array on validation errors was read off the raw (still-enveloped) body and was
  therefore always `undefined`.
- The diagnosis proposed a new `body?.detail ?? body` unwrap variant. Rejected in favor of
  the project's already-established `parsed?.detail && typeof parsed.detail === 'object' ?
  parsed.detail : parsed` idiom (copied verbatim from `voicePassClient.ts`) — the two are
  functionally equivalent across every realistic body shape (enveloped dict, plain-string
  detail, 422 array, bare-string body), but the established idiom wins on consistency: all
  8 sibling client files now read identically, rather than 5 in one style and 3 in another.
- The lesson this whole bug encodes: `findingsClient.test.ts` already asserted this exact
  unwrapping behavior via a fetch-stub against the real parse path — which is precisely why
  `findingsClient.ts` was correct and `reviewClient.ts`/`signOffClient.ts`/`contentPatchClient.ts`
  were not (their sibling test files, e.g. `DecisionRail.test.tsx`, constructed the error
  object directly instead of testing the parse path). **Test the parse path, not a
  hand-constructed error object.**
