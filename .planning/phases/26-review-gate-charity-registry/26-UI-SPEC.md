## Spacing Scale

Declared values (multiples of 4 — matches existing dashboard Tailwind pattern):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline badge padding |
| sm | 8px | Compact element spacing (button icon gap, tag gap) |
| md | 16px | Default element spacing (panel internal padding, form field gap) |
| lg | 24px | Section padding (panel `p-5` = 20px is used today; treat 24px as the target for new panels) |
| xl | 32px | Layout gaps (between page-level panels, `space-y-8` in settings page) |
| 2xl | 48px | Major section breaks (iframe chrome separation from controls) |
| 3xl | 64px | Not used in this phase |

Exceptions:
- Touch targets: minimum 44px height and width on all interactive elements (already enforced in existing components via `min-h-[44px]` / `min-w-[44px]` — maintain this across ALL new buttons, toggles, and checkboxes in Phase 26).
- The preview iframe panel has no internal padding — the iframe fills the chrome edge to edge so the full magazine layout is unobstructed.
- Claims checklist rows: 40px row height acceptable (text + checkbox pair with 8px vertical padding each side) — slightly below 44px because the rows are list items, not primary actions. The row's skip/check buttons individually meet 44px.

## Typography

Source: existing dashboard pages confirm exactly two weights in active use. Size difference (`text-xs` vs `text-sm`) provides sufficient role distinction for labels without requiring a third weight.

| Role | Size | Weight | Line Height | Usage |
|------|------|--------|-------------|-------|
| Body | 14px (text-sm) | 400 (regular) | 1.5 | Table cells, panel body text, checklist claim text, registry row data |
| Label | 12px (text-xs) | 400 (regular) | 1.4 | Section eyebrows, column headers, badge labels, status tags, cost rollup labels |
| Heading | 16px (text-base) | 600 (semibold) | 1.25 | Panel section headers (h2), cost summary heading, checklist section title |
| Page title | 20px (text-xl) | 600 (semibold) | 1.25 | Page-level h1 — matches existing `text-xl font-semibold` on Runs / Settings pages |

Exactly two weights: 400 (regular) and 600 (semibold). Do not introduce `font-medium` (500) in any component. Use size (`text-xs` vs `text-sm`) to distinguish label roles from body roles.

Source: `RunControlBar.tsx` (`text-xl font-semibold`), `BudgetAlertBanner.tsx` (`text-sm`), `SettingsPage` (`text-sm text-neutral-500`).

No additional sizes. Do not introduce display type — this is an operator utility dashboard, not editorial UI.

## Color

Source: `apps/dispatch-control/app/globals.css` CSS custom properties (confirmed). All color references must use the CSS variable token system (`text-neutral-*`, `bg-neutral-*`, `border-neutral-*`, `text-red-*`, etc.) — no hardcoded hex values in component source.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background: #ffffff` | Page background, card/panel surfaces, iframe chrome |
| Secondary (30%) | `--secondary: #f5f5f5` / `--muted: #f5f5f5` | Table row stripes (alternating), panel inset backgrounds, claims checklist row hover |
| Accent (10%) | `--primary: #171717` | CTA buttons (Approve and Publish, Approve and Schedule), active toggle state, primary action indicators |
| Destructive | `--destructive: #ef4444` | Reject run button, blocklist action, `auto_publish` alarming state |
| Warning | `border-amber-200 bg-amber-50 text-amber-800` | Budget alert banner (existing pattern — reuse for any non-destructive warnings) |

**Accent reserved for:** approve-and-publish CTA button, approve-and-schedule CTA button, registry "Add Charity" primary button. Nothing else. All other interactive elements use neutral or outlined styling.

**`auto_publish` alarming treatment:** When `auto_publish=true`, render a persistent red banner using the `border-red-200 bg-red-50 text-red-700` pattern (mirrors the existing "Danger Zone" panel in `config/page.tsx` — `border border-red-200`). The `auto_publish` toggle itself renders as a red destructive-styled button at all times (not a neutral toggle). The confirmation modal uses `--destructive` for the confirm action.

Source: `config/page.tsx` Danger Zone panel pattern (`border-red-200 bg-white`) — reuse for `auto_publish`-enabled warning banner.

## Screens and Interaction Contracts

### Screen 1: Review Queue (within `/runs` page or `/runs/review` sub-section)

**Layout:** The existing `/runs` page gains an "Awaiting Review" panel above the run history table. Each awaiting-review row links to the full review screen at `/runs/[runId]/review`.

**Awaiting-review run card fields:**
- Issue number + charity name (from run metadata)
- Run started at (relative time)
- Estimated cost (reads `pipelineRuns.costUsd`)
- Status badge: "Awaiting Review" (amber)
- Primary action link: "Review" → `/runs/[runId]/review`

### Screen 2: Review Screen (`/runs/[runId]/review`)

**Layout contract (D-10):** Preview-centric. Two-column on ≥1280px:
- LEFT COLUMN (≈64% width): Preview iframe — fills the column edge to edge. The iframe loads the token-guarded draft-preview route on `apps/web`. Height = viewport minus header chrome (approximately `calc(100vh - 64px)`), scrollable independently.
- RIGHT COLUMN (≈36% width, sticky): Vertical stack from top to bottom:
  1. Cost summary (read-only card)
  2. Factual claims checklist (RVW-05) — scrollable if long
  3. Decision actions (approve/schedule/reject/re-roll)

On <1280px (narrow viewport): single column — decision controls collapse into a fixed bottom bar (64px height) with "Approve and Publish" + an overflow menu ("Schedule / Reject / Re-roll"). The iframe stacks above and takes 60vh.

**Preview iframe:**
- `<iframe src={previewUrl} title="Issue preview" className="w-full h-full border-0" />` — no border, no padding.
- Show a skeleton loader while the iframe is loading (`onLoad` event).
- Show the error copy "Preview unavailable…" if the iframe returns a non-200 (detect via `srcdoc` postMessage or HTTP status on the token endpoint).

**Approve button disabled states:**
- Disabled when `claimsQuery.status !== 'success'` (loading guard — prevents false-enabled flash per RESEARCH Pitfall 5).
- Disabled when any claim has `status: 'pending'`.
- Enabled only when `claimsQuery.status === 'success' && allSignedOff === true`.

### Screen 3: Charity Registry (`/charities`)

**Layout:** Standard dashboard page. Single column, `space-y-6`.

**Top bar:** "Charity Registry" h1 (left) + "Add Charity" button (right, primary style).

**Filter bar (below top bar):** Three pill toggles — "All", "Candidates", "Featured", "Blocklisted". Active state = filled neutral-900 background; inactive = outlined. Selecting a pill filters the table.

**Registry table columns:**
- Name (text-sm, left-aligned)
- Website (text-sm, muted, truncated at 32 chars with ellipsis)
- Status badge (candidate / featured / blocklisted — color-coded: neutral for candidate, green-tinted for featured, red-tinted for blocklisted)
- Times Featured (text-sm, numeric, right-aligned)
- Last Featured (relative time, text-xs muted)
- Actions column: status toggle button (e.g., "Blocklist Charity" or "Remove from Blocklist") — text-sm, no background, `text-neutral-600 hover:text-neutral-900`

### Screen 4: `auto_publish` Toggle (within `/config` AutomationPanel)

**Position:** Below the existing schedule toggle in the AutomationPanel, within a visually separated "Advanced" subsection with a `border-t border-neutral-200 mt-4 pt-4` separator.

**Enabled state appearance:**
- A persistent `border-red-200 bg-red-50 text-red-700` banner appears at the top of every page in the dashboard (injected in the dashboard layout, not per-page). Text: "Auto-publish is enabled. Runs will publish automatically without review."
- The banner has a direct link to `/config` — "Change in Config".
- The toggle button in the config page changes to a destructive-red style.

**Modal for enabling:** Uses shadcn `Dialog`. Non-dismissible — no X button, no click-outside-to-close (the operator must explicitly choose Enable or Cancel). Modal background is not blurred — the page is dimmed with `bg-black/40` overlay so the alarming banner context is still partially visible.

## Accessibility

Carry-forward from existing dashboard components — all apply to Phase 26:

- `min-h-[44px] min-w-[44px]` on all interactive targets.
- `focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-neutral-900 focus-visible:ring-offset-1` on all interactive elements.
- `role="alert"` on any banner that appears dynamically.
- `role="log" aria-live="polite"` on the claims checklist if it updates in real time.
- `aria-disabled` + `title` tooltip on the disabled Approve button (explains why it is disabled).
- The preview iframe: `title="Issue preview"` attribute required.
- The `auto_publish` enable modal: trap focus within the dialog while open (`shadcn Dialog` handles this via Radix).
- All status badges use text labels (not color alone) — color is additive, not the sole signal.
- Claims checklist keyboard navigation: each claim row's Check and Skip buttons are individually focusable in document order.
